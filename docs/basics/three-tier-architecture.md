# Трёхзвенная архитектура в 1С: клиент, сервер и СУБД

Разбираемся, как устроена клиент-серверная работа 1С: кто из трёх звеньев за что отвечает, зачем клиенту посредник перед базой данных и как масштаб задачи подсказывает, какую схему выбирать.

Материал продолжает статью [«Платформа 1С: что это и как она запускается»](platform.md). Там мы выяснили, какие бывают режимы запуска 1С и что ещё выбирается при старте. Здесь подробно разбираем один из таких выборов — вариант работы базы.

## Что такое трёхзвенная архитектура

**Трёхзвенная архитектура** — способ построения системы, при котором работа разделена между тремя «этажами» — звеньями. Каждое звено делает своё, передаёт результат следующему и не лезет в чужие дела:

1. **Клиент** — программа на компьютере пользователя: тонкий клиент, веб-клиент (или толстый — в старых решениях). Показывает формы, принимает клики, рисует таблицы. Тяжёлую работу не выполняет.
2. **Сервер 1С:Предприятия** — «мозг» системы. Здесь выполняется серверный код на встроенном языке 1С: проведение документов, расчёты, формирование отчётов. Сервер также следит, чтобы пользователи не мешали друг другу.
3. **СУБД** (система управления базами данных) — программа, специально созданная для хранения данных: PostgreSQL, MS SQL и другие. Держит всё на диске и очень быстро записывает и находит данные по запросам сервера 1С.

Данные движутся по цепочке: клиент ↔ сервер 1С ↔ СУБД. Обратите внимание: клиент никогда не общается с СУБД напрямую — всегда через сервер 1С.

```
[ Клиент ]  ←→  [ Сервер 1С ]  ←→  [ СУБД ]
 интерфейс       бизнес-логика       данные
```

Те же три звена в терминах ресторана:

| Звено | В ресторане | В 1С |
|---|---|---|
| Клиент | Зал: гость смотрит меню и делает заказ | Экран с формами и кнопками |
| Сервер 1С | Кухня: повара готовят блюдо по заказу | Выполняет прикладную логику |
| СУБД | Склад: хранит продукты, выдаёт по накладным | Хранит и выдаёт данные |

Гость не ходит на склад сам — заказ идёт через кухню. Так и пользователь не «достаёт» данные из базы руками: за него это делает сервер.

## Почему архитектура именно такая

Польза среднего звена — сервера 1С — проще всего видна, если представить, что его нет. Такая схема называется **двухзвенной** — и это не мысленный эксперимент: в 1С 7.7 отдельного сервера 1С ещё не было, и каждая копия платформы ходила в СУБД напрямую. Вот какие проблемы у неё всплывают:

- **Нагрузка на рабочие места.** Всю обработку тянет компьютер пользователя — ему нужна мощная машина.
- **СУБД захлёбывается соединениями.** Каждому клиенту нужно своё подключение к базе: десять пользователей — десять соединений, тысяча — тысяча. А СУБД устроены наоборот: они рассчитаны на несколько мощных подключений от серверов, через которые идут большие потоки данных, — а не на множество мелких клиентских. Каждое лишнее подключение — это память на сервере СУБД, а у платных СУБД ещё и лишние лицензии.
- **Правила разбегаются.** Бизнес-логика («нельзя провести документ с нулевой суммой») живёт на каждом клиенте. Кто-то её перепишет, кто-то забудет обновить — и данные теряют целостность.
- **Безопасность.** В базу может постучаться кто угодно: пароль от неё раздаётся всем рабочим местам.

Сервер 1С в середине закрывает все четыре проблемы:

- тяжёлые вычисления переезжают на сервер — клиенту достаточно рисовать интерфейс;
- с СУБД работает только сервер: вместо тысячи лёгких клиентских соединений — несколько мощных и быстрых;
- бизнес-правила живут в одном месте, на сервере, и пользователь не может их обойти;
- обновили сервер — обновились все клиенты сразу.

Аналогия со складом. Плохая схема: каждый покупатель сам ходит между стеллажами со своей накладной — толкучка, перепутанные полки, чужие коробки. Хорошая схема: на склад пускают только кладовщика (сервер 1С), а все получают товар через него по заявкам. Порядок гарантирован.

!!! note "А где файловая база?"
    В файловом варианте отдельного сервера нет: платформа на компьютере пользователя сама выполняет работу всех трёх звеньев — и «сервера», и СУБД. Все этажи оказываются в одном здании.

## Кластеры: когда одного сервера мало

**Кластер серверов 1С** — несколько серверов 1С, которые работают как единое целое. Внутри есть центральный сервер — диспетчер, который раздаёт работу остальным.

Зачем объединять серверы:

- **Балансировка нагрузки.** Много пользователей и много баз — сеансы распределяются между серверами, никто не стоит в очереди.
- **Отказоустойчивость.** Если один сервер упал, его сеансы подхватывают другие (при настроенном резервировании) — пользователи почти ничего не замечают.
- **Обслуживание без остановки.** Один сервер можно обновить или перезапустить, пока остальные продолжают работать.

Аналогия: сеть ресторанов с общей диспетчерской. Заказы уходят на ту кухню, где свободнее; закрылась одна на ремонт — заказы готовят остальные.

!!! note "А если сломается машина с базой?"
    Кластер серверов 1С защищает только серверы 1С. Резервированием базы занимается сама СУБД: основной сервер базы работает в паре с резервным, который непрерывно получает копию данных — реплику. Основной упал — резервный подхватывает, как склад-дублёр с копией всех запасов, а 1С просто подключается к новому адресу.

    Кластер СУБД настраивается средствами выбранной СУБД (PostgreSQL, MS SQL и т.д.), платформа 1С его не строит — лишь подключается к адресу, который ей указали. Поэтому «кластер» в мире 1С и в мире СУБД — разные механизмы, хотя слово одно.

## Какие СУБД может использовать 1С

В файловом варианте используется **встроенная файловая СУБД** платформы — ставить ничего не нужно. Для клиент-серверного варианта платформа официально поддерживает четыре серверные СУБД:

| СУБД | Лицензия | Где обычно встречается |
|---|---|---|
| PostgreSQL | Бесплатная, открытый код | Самый частый выбор для новых проектов; есть сборки, адаптированные для 1С (например, Postgres Pro) |
| Microsoft SQL Server | Платная | Компании с Windows-инфраструктурой |
| Oracle Database | Платная | Крупные проекты с высокими нагрузками |
| IBM Db2 | Платная | Компании, где Db2 уже стоит много лет и менять его никто не собирается; для новых проектов выбирается редко |

## Как масштаб влияет на выбор архитектуры

Архитектуру определяет не мода, а масштаб: сколько людей работает с базой одновременно и какой объём данных они гоняют.

| Масштаб | Схема | Что ставить |
|---|---|---|
| 1–3 человека, учебная база | Файловый вариант | Ничего: платформа и папка с базой на одном ПК |
| Небольшая фирма, единицы–десятки пользователей | Клиент-серверная, всё на одном сервере | Сервер 1С + СУБД (обычно PostgreSQL) на одной машине |
| Средний бизнес, десятки–сотни пользователей, много баз | Клиент-серверная, звенья разнесены | Сервер 1С и СУБД на отдельных машинах; при нагрузке — кластер серверов 1С |
| Крупный бизнес, сотни–тысячи пользователей, работа без остановок | Кластеры | Кластер серверов 1С + отказоустойчивая СУБД |

Аналогия с пиццерией. Один пекарь и одна печь на район — файловый вариант. Пекарня с несколькими поварами — клиент-серверная схема на одном сервере. Сеть пекарен с диспетчерской и запасными печами — кластеры.

Практическое правило: **начинают с малого и переезжают, когда база подросла.** Ставить кластер «на вырост» — переплата за мощности, которые годами простаивают. Переезд из файла на сервер — штатная операция платформы: конфигурация и данные переносятся, ничего переписывать не нужно.

## Файловый режим и файл 1Cv8.1CD

**Файловый вариант** — вся информационная база живёт в обычной папке на диске. Путь к папке задаётся при создании базы и виден в списке баз в окне запуска 1С — например, `C:\1C\Bases\Бухгалтерия`.

Главный файл в этой папке — **`1Cv8.1CD`**. Это фирменный «контейнер» 1С, в котором лежит всё содержимое базы: и конфигурация, и все данные. Размер этого файла примерно равен размеру базы. Рядом платформа создаёт служебные файлы — кэш, журнал и прочее, — но сама база — это прежде всего `1Cv8.1CD`.

Кто исполняет звенья в файловом режиме? Сама платформа на вашем компьютере: она и «сервер», и «СУБД». Поэтому файловая база:

- **не требует серверов** — ни сервера 1С, ни сервера СУБД, администрировать нечего;
- **легко переносится** — скопировал папку на флешку или другой ПК — перенёс базу;
- **легко резервируется** — копия папки и есть резервная копия;
- **но рассчитана на маленькие команды**: при одновременной активной работе многих пользователей база тормозит, а файл можно повредить.

!!! warning "Осторожно с копиями"
    Копировать файл `1Cv8.1CD` (и вообще выгружать базу) можно только когда с ней никто не работает — иначе копия может оказаться «недописанной» и не открыться. Надёжные способы: штатная выгрузка в файл `.dt` (раздел «Администрирование») или копия папки при выключенных сеансах.

## Что запомнить

- Трёхзвенная архитектура: **клиент** (интерфейс) → **сервер 1С** (бизнес-логика) → **СУБД** (данные). Клиент не общается с СУБД напрямую.
- Сервер в середине решает главные проблемы: снимает тяжесть с компьютеров пользователей, разгружает СУБД, хранит бизнес-правила в одном месте.
- **Кластер серверов 1С** — несколько серверов как один: балансировка и отказоустойчивость. База тоже может резервироваться (кластер СУБД), но это продвинутый уровень — он настраивается средствами самой СУБД.
- Серверные СУБД для 1С: PostgreSQL, Microsoft SQL Server, Oracle Database, IBM Db2 (плюс встроенная файловая СУБД в файловом варианте).
- Масштаб решает: один пользователь — файловая база; десятки — один сервер 1С + СУБД; сотни и больше — кластеры.
- Файловая база — это папка, главный файл — `1Cv8.1CD`; резервная копия — его копия при выключенных сеансах или выгрузка в `.dt`.
